# Stella Sharm Tours release audit

**Hold the production launch.** A clean PostgreSQL setup rejects the current catalog. Sixteen itinerary stops across three trips have no recorded time, while the seed schema requires a string. All 52 backend integration cases consequently skipped during setup. An independent restore test also could not start Docker. On an existing populated database, a separate defect lets an authorized homepage edit interrupt catalog reads and booking requests. The production dependency audit also found a high-severity advisory. The application built successfully, all 112 unit tests passed, and lint and typechecking passed. Those are useful results for the code they exercised. [Seed schema](F:/stella-project-kit/packages/db/src/seed-data.ts:61) · [Database test setup](F:/stella-project-kit/apps/api/src/backend.integration.test.ts:212) · [Advisory](https://github.com/advisories/GHSA-fc5q-39xc-vjpf)

**Scope.** Working checkout on 18 November 2026, branch `admin-rebuild`, commit `b3f7fac` plus the uncommitted changes present during review. The source findings below describe reachable code paths and their conditions. The browser observations came from local production builds using a read-only catalog fixture. Production incidents, the actual VPS configuration, authenticated staff journeys, field performance and native-speaker approval remain unverified. The companion appendix covers the seven languages individually, verification scope and additional findings. ## Release decision and fix order

**First restore the evidence.** Repair the seed and browser selectors, run PostgreSQL and restore tests in a clean environment, and resolve the dependency advisory against the image actually intended for release. Make these checks mandatory for the exact commit being promoted.

**Then protect the customer and staff journeys.** Prioritize live hero validation, media revocation, mixed and unavailable itineraries, service-date pricing, retry safety, preservation of staff edits and seven-language publication. Use staff-edited content, seasonal rates, a withdrawn trip and a delayed save in the acceptance dataset. Run one full booking through storage, staff notification, customer confirmation and an authorized staff update.

**Before opening production traffic**, verify deployment isolation, privilege boundaries, alert delivery and an off-site restore, then record approval of public content, media and legal pages. Repeat the mobile measurements and document residual risks with a named owner and verification date. This sequence gives staff a working recovery path before they rely on the dashboard for live bookings.
